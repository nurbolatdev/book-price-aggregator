# Производительность

Замер публичного read-API (поиск и карточка издания) нагрузочным тестом k6 против локального стека `docker compose`. Цели — `docs/01-architecture.md`, раздел 7.

## Окружение

| Параметр | Значение |
|---|---|
| Машина | Apple M4, 16 ГБ RAM, macOS 15.6 |
| Docker | 29.4.1, Docker Desktop: 10 CPU, 8 ГБ RAM |
| Стек | `docker compose` (backend, postgres 16, redis 7, rabbitmq 3.13, mailpit, frontend), профиль `docker,demo` |
| Данные | 87 книг, 98 изданий, 122 предложения, 490 записей истории цен (демо-каталог), 3 включённых магазина |
| Лимиты запросов | выключены на время замера (`RATE_LIMIT_ENABLED=false`), иначе 20 VU с одного IP упираются в 60 запросов поиска в минуту и измеряют ответы 429 |

## Параметры k6

Сценарий — `infra/k6/search.js`: 20 VU, 1 минута, пауза 0.5-1 с между итерациями. Около 70% запросов — `GET /api/v1/search?q=...`, около 30% — `GET /api/v1/editions/{id}` (идентификаторы собираются в `setup()` поиском по фиксированным запросам).

- **Холодный кэш:** `FLUSHALL` в Redis, перезапуск backend, `SCENARIO=cold`. Каждый запрос поиска — слово или фамилия, по которым в демо-каталоге есть результаты (21 запрос), в сочетании с одной из 4 сортировок и размером страницы 5-50, так что ключ кэша в этом прогоне ещё не встречался. Доля непустых ответов считается метрикой `search_nonempty`. Для карточек в холодном прогоне измеряется только первое обращение к каждому идентификатору (тег `edition_first`); повторные обращения идут с тегом `edition` и в строку холодного кэша не входят.
- **Тёплый кэш:** сразу после холодного прогона, без сброса, короткий список из 10 запросов (часть из них, например `linux`, пустые, поэтому доля непустых ответов ниже).

## Результаты

| Запрос | Кэш | p50 | p95 | Цель | Итог |
|---|---|---|---|---|---|
| Поиск | холодный | 7.6 мс | 14.5 мс | p95 < 500 мс | выполнено |
| Поиск | тёплый | 5.6 мс | 7.8 мс | p95 < 200 мс | выполнено |
| Карточка издания (первое обращение) | холодный | 9.7 мс | 73.5 мс | p95 < 300 мс | выполнено |
| Карточка издания | тёплый | 4.2 мс | 6.4 мс | p95 < 300 мс | выполнено |

Во всех прогонах 0% ошибок, около 1600 итераций (26 итераций в секунду; потолок задаёт пауза в сценарии, а не приложение).

Доля непустых ответов поиска (`search_nonempty`): холодный прогон 100% (1097 из 1097), тёплый 90.8% (1039 из 1144). Холодный поиск теперь измеряет реальные запросы с результатами и выборкой из БД; прежние числа были занижены, потому что двусловные комбинации в основном возвращали пустой ответ. Первое обращение к карточке дороже поиска (p95 73.5 мс): нужно собрать предложения и историю цен, но цель 300 мс выполнена с запасом.

### Отказ зависимостей (`GET /api/v1/admin/health`)

| Остановлено | Ответ | Компонент | Публичный API |
|---|---|---|---|
| ничего | 200, общий статус `UP` | все `UP` | - |
| Redis | 200, общий статус `DOWN`, ответ за 4.1 с (таймаут команды) | `redis`: `DOWN`, `Redis command timed out` | поиск отвечает 200, но 2 с (запрос идёт в БД, кэш недоступен) |
| RabbitMQ | 200, общий статус `DOWN` | `rabbit`: `DOWN`, `UnknownHostException: rabbitmq` | поиск отвечает 200 за 8 мс |

После запуска сервисов обратно статус возвращается в `UP`.

## Как повторить

Нужен запущенный стек с демо-каталогом (`SPRING_PROFILES_ACTIVE=docker,demo`).

```bash
# 1. В .env выставить RATE_LIMIT_ENABLED=false и перезапустить backend
docker compose up -d backend

# 2. Холодный прогон
docker exec kitapradar-redis redis-cli FLUSHALL
docker restart kitapradar-backend   # дождаться healthy
docker run --rm -i --network kitapradar_default \
  -e BASE_URL=http://backend:8080 -e SCENARIO=cold \
  grafana/k6 run - < infra/k6/search.js

# 3. Тёплый прогон
docker run --rm -i --network kitapradar_default \
  -e BASE_URL=http://backend:8080 \
  grafana/k6 run - < infra/k6/search.js

# 4. Вернуть RATE_LIMIT_ENABLED=true и перезапустить backend
```

Пороги в сценарии повторяют цели из архитектуры: прогон завершается с ошибкой, если p95 выше цели.

## Оговорки

- Одна машина: k6, приложение, PostgreSQL, Redis и RabbitMQ работают на одном хосте и делят ресурсы.
- Каталог маленький (98 изданий): индексы и кэш PostgreSQL целиком в памяти. На каталоге в сотни тысяч записей числа будут хуже, особенно холодный поиск.
- Лимиты запросов выключены, поэтому замер не показывает поведение при 429.
- Нагрузка постоянная и небольшая (около 26 запросов в секунду), это проверка целей из раздела 7, а не поиск предела.
- Парсеры в замере не запускались.

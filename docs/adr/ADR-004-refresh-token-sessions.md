# ADR-004: Сессии на семействах refresh-токенов, лимит устройств и очистка токенов

**Статус:** принято · **Дата:** 2026-10-23 · **Веха:** M18 (сверх плана, согласовано при приёмке)

## Контекст
В M18 появились refresh-токены с ротацией: каждое обновление отзывает использованный токен и выдаёт новый. По заданию повторное предъявление отозванного токена (признак кражи) отзывало **все** токены пользователя. Остались открытые вопросы:
- одна украденная сессия выбрасывала пользователя со всех устройств;
- число одновременных сессий не ограничено;
- истёкшие и отозванные токены и ссылки из писем копятся в базе бессрочно;
- нужен след для разбора инцидентов, но без хранения лишних персональных данных.

## Решение
1. **Семейство токенов = одна сессия.** Колонка `refresh_tokens.family_id` (миграция V14). Вход создаёт семейство, ротация его сохраняет. Повтор отозванного токена отзывает только его семейство, другие устройства пользователя остаются в системе. Сброс пароля по-прежнему отзывает все сессии.
2. **Лимит сессий** `app.jwt.max-sessions` (по умолчанию 10, `JWT_MAX_SESSIONS`). Вход сверх лимита завершает сессию, которая дольше всех не обновлялась (LRU: время последнего обновления = время создания действующего токена семейства). Вход блокирует строку пользователя (`SELECT … FOR UPDATE`), чтобы одновременные входы не превышали лимит.
3. **Очистка по сроку хранения**, а не по факту отзыва. Ночной `CleanupScheduler` (ShedLock, 03:30 Asia/Almaty) вызывает `TokenCleanupService`:
   - refresh-токены — через 30 дней после `expires_at`, отозванные или нет;
   - ссылки из писем — через 7 дней после `expires_at`, использованные или нет;
   - пакетами по 1000 строк, каждый пакет — отдельная транзакция; индексы по `expires_at` (V15);
   - сроки и размер пакета — `app.auth.cleanup.*`.
4. **Аудит — в `system_events`, а не в таблицах токенов.** При повторе токена пишется WARN (источник `auth`): `userId`, `familyId`, User-Agent (до 255 символов), время. Не пишутся: сам токен, его хеш, IP-адрес (персональные данные, решение владельца проекта).
5. **Старые токены (до V14).** Цепочки ротации раньше не хранились и не восстанавливаются, поэтому все старые токены пользователя объединяются в одно семейство (`md5('legacy-refresh-family:' || user_id)::uuid`). Повтор старого токена завершает все старые сессии пользователя — как до семейств, без ослабления защиты.

## Почему
- Отозванный, **но ещё не истёкший** токен нельзя удалять: без его записи повтор станет «неизвестным токеном» и кража не обнаружится. После истечения токен бесполезен для всех, поэтому правило удаления — «N дней после `expires_at`».
- Семейства сохраняют защиту от кражи (сессия вора завершается), но не наказывают остальные устройства пользователя.
- Пакетное удаление в отдельных транзакциях не держит долгие блокировки даже при большом накоплении.
- Таблица токенов — плохой журнал (только хеши, нет описания события); `system_events` уже есть (M15) и читается админкой (M20).

## Рассмотренные варианты очистки
| Вариант | Итог |
|---|---|
| Плановая задача в приложении + DELETE пакетами | **выбран**: просто, в коде, покрыт тестами, ShedLock уже есть |
| Удаление своих старых токенов при входе | только дополнение: не чистит неактивных пользователей |
| `pg_cron` в PostgreSQL | отклонён: расширение и настройка образа, логика вне кода и тестов |
| Партиционирование по месяцам + DROP PARTITION | отклонён: нужно при миллионах строк, у нас тысячи |
| Refresh-токены в Redis с TTL | отклонён: теряются SQL, транзакционная ротация и обнаружение повтора |

## Последствия
- (+) Кража токена завершает одну сессию и оставляет след в журнале; остальные устройства работают.
- (+) Таблицы токенов не растут бесконечно; не больше 10 сессий на пользователя.
- (−) **Окно обнаружения повтора ограничено**: отозванный токен хранится до 60 дней от выдачи (30 жизни + 30 хранения). Предъявленный позже, он «неизвестен» → 401 без отзыва семейства. К этому времени обычно истекает и цепочка вора, если её не обновляли.
- (−) Лимит сессий сериализует входы одного пользователя (блокировка строки на время входа — миллисекунды).
- (−) Старые токены одного пользователя после V14 — одна сессия: повтор старого токена завершает все старые сессии сразу.

## Проверка
- `RefreshTokenIT`: повтор завершает одну сессию, другое устройство работает, событие без токена и с обрезанным User-Agent; 11-й вход завершает самую давнюю **по обновлению** сессию; два одновременных входа при 9 сессиях дают ровно 10 (без блокировки тест падает с 11).
- `TokenCleanupServiceIT`: удаляется только старше срока хранения; точная граница ±1 с; несколько пакетов; повтор отозванного токена после очистки по-прежнему ловится.
- `MigrationIT`: после V14 старые токены пользователя — одно семейство, у разных пользователей — разные (нужен Docker; вручную проверено на локальной базе, поднятой миграциями V1–V13).

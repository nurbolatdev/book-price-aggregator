# ADR-005: Refresh-токен в cookie и окно повтора

**Статус:** принято · **Дата:** 2026-10-29 · **Веха:** M22 (уточняет ADR-004)

## Контекст
- Frontend F1 хранит refresh-токен в `localStorage`: любой XSS на странице может его прочитать и унести.
- По ADR-004 повтор отозванного токена завершает сессию. Две вкладки одного браузера, обновляющие пару одновременно, предъявляют один и тот же токен: вторая выглядит как кража, и пользователя выбрасывает из системы.
- Смена пароля должна оставлять текущее устройство, но cookie с `Path=/api/v1/auth` на `/api/v1/me/password` не отправляется.

## Решение
1. **Cookie `kr_refresh`:** `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth; Max-Age` = срок жизни refresh-токена. `Secure` управляется `app.jwt.refresh-cookie-secure` (`REFRESH_COOKIE_SECURE`, по умолчанию `true`; в профиле `local` — `false`). `Path=/api/v1/auth` — cookie не уходит на остальные вызовы API.
2. **Источник токена:** `refresh` и `logout` берут cookie, затем тело. Без токена `refresh` отвечает 401, `logout` — 204. Выход, `logout-all`, сброс пароля и удаление аккаунта очищают cookie (`Max-Age=0`); смена пароля не очищает (текущее устройство остаётся).
3. **Проверка `Origin`** на `refresh` и `logout`: заголовок есть и не входит в `app.cors.allowed-origins` → 403; заголовка нет, а токен из cookie → 403; заголовка нет и токен из тела → разрешено (curl, тесты, переходный режим: токен в теле не передаётся браузером сам, CSRF невозможен). CORS отдаёт `Access-Control-Allow-Credentials: true`.
4. **Переходный режим:** `refreshToken` остаётся в теле запросов и ответов (помечен `deprecated`), чтобы F1 работал; убрать в F4 вместе с переходом frontend на cookie.
5. **Текущая сессия для `/me/password`:** access-токен получает claim `sid` (id семейства refresh-токенов). Порядок определения: `sid` → `refreshToken` в теле (переходный режим) → ничего (отзываются все сессии).
6. **Окно повтора 10 с** (`app.jwt.refresh-reuse-grace`, `JWT_REFRESH_REUSE_GRACE`). Следующий токен при ротации вычисляется: `HMAC-SHA256(app.jwt.secret, "kr-refresh-successor:" + предыдущий токен)`, base64url без паддинга. Отозванный токен, предъявленный в пределах окна от `revoked_at`, проходит цепочку преемников (не больше 3 шагов) до того, что совпал по хешу с действующим токеном семейства, и получает его вместе с новым access-токеном (событие INFO). Нет совпадения (семейство отозвано выходом, сменой пароля, лимитом сессий) или окно истекло — прежний путь: семейство отзывается, WARN, 401. В БД по-прежнему только хеши.
7. **Параллельные запросы** с одним токеном выстраиваются на блокировке строки (`SELECT … FOR UPDATE` в `findByTokenHash`).
8. **Выход завершает всё семейство** предъявленного токена в любом состоянии, а не только действующий токен: иначе вкладка, вышедшая с токеном, ротированным секунду назад другой вкладкой, оставила бы сессию живой.

## Рассмотренные варианты
| Вариант | Итог |
|---|---|
| Копия сырого токена в Redis на 10 с | Отклонён: сырой токен вне БД и зависимость `refresh` от Redis |
| Выдавать второй токен в семействе | Отклонён: два действующих токена на одну сессию |
| `Path=/api/v1` | Отклонён: cookie уходила бы на каждый вызов API |
| Остаться на `localStorage` | Отклонён: токен доступен любому XSS |

## Последствия
- Утечка `app.jwt.secret` позволяет вычислить преемников украденного токена; но тогда можно подделывать и access-токены, поэтому риск не растёт.
- F4 обязан перейти на cookie и использовать Web Locks, чтобы вкладки не обновляли пару одновременно (окно — страховка, а не замена).
- Safari может игнорировать `Secure` на `http://localhost`; в dev используется `REFRESH_COOKIE_SECURE=false`.
- Следующий токен при ротации определяется предыдущим однозначно.

## Проверка
- `RefreshCookieIT` — атрибуты cookie, очистка, источник токена, `Origin`, CORS.
- `RefreshReuseGraceIT` — параллельный refresh, повтор вне окна, выход и смена пароля в окне, цепочка T0→T1→T2.
- `RefreshTokenIT` — повтор вне окна завершает семейство.

# Отчёт M19 — маячки и уведомления: как работает, решения, гарантии доставки

**Ветка:** `feature/m19-beacons-notifications` · **Дата:** 2026-10-23 · **Для:** рецензента

Задание вехи — [M19-beacons-notifications.md](M19-beacons-notifications.md). Здесь — как система устроена, какие решения приняты и почему, что прошло ревью, какие риски остаются.

## 1. Как это работает
```
Пользователь ──POST /beacons──► beacons (baseline = текущая лучшая цена)

Парсер меняет цену ─► offers + PriceChangedEvent ─(после коммита)─► kr.events / price.changed
        ├─► kr.price-changed.cache   → сброс кэша карточки
        └─► kr.price-changed.beacons → BeaconChecker
               1. лучшая цена в наличии (MATCHED, магазин включён)
               2. маячки ACTIVE + TRIGGERED, пачками по 500, строки под FOR UPDATE
               3. условие выполнено И цена — новый минимум → TRIGGERED, notifications (QUEUED, delivery)
               4. INSTANT → после коммита: публикация письма с подтверждением брокера → published_at
                  DIGEST  → ждёт DigestScheduler (09:00 Алматы)
                                                   │
kr.notify.email ─► EmailListener: строки уведомления FOR UPDATE (ждём другую копию / relay)
                    уже SENT или закрыто окончательно? → ack без отправки
                    иначе SMTP → SENT (та же транзакция) → снять блокировку → ключ Redis → ack
                    ошибка SMTP → откат → FAILED (временная причина) → повтор RabbitMQ (3 попытки) → DLQ

BeaconEmailRelay (раз в минуту): QUEUED + INSTANT + published_at IS NULL + старше 1 мин → опубликовать снова;
                                 старше 24 ч → FAILED / NOT_PUBLISHED
```

## 2. Продуктовые правила (контракт)
| Правило | Поведение |
|---|---|
| Условия | `ANY_DROP`: ниже baseline; `BELOW_PRICE`: ≤ цели; `DISCOUNT_PERCENT`: ≤ baseline × (100 − p)/100, без округления |
| Когда письмо | Только о **новом минимуме** относительно последней сообщённой цены. 3 500 → 3 200 — да; 3 200 → 3 200 — нет; → 3 000 — да; 3 000 → 3 800 → 3 000 — **нет**; → 2 950 — да |
| После срабатывания | Маячок остаётся `TRIGGERED` и следит дальше; `PAUSED` не проверяется |
| Перевзвод | Возврат в `ACTIVE` или смена условия: baseline = текущая лучшая цена, отсчёт минимумов заново |
| Email не подтверждён | Маячок срабатывает (виден в UI), письма нет, `FAILED` / `EMAIL_NOT_VERIFIED` |
| `SENT` | Почтовый сервер **принял** письмо; не означает «доставлено во входящие» |
| Сводка | Пользователь с `DAILY`: одно письмо в 09:00 Алматы; у маячка — последняя цена; удалённые / на паузе → `BEACON_INACTIVE` |
| Способ доставки | Фиксируется при срабатывании; смена настройки потом не переносит уведомление между письмом и сводкой |

## 3. Гарантии доставки: сценарии отказа
Цель — **не терять письма**; доставка «хотя бы раз», дубли редки. «Ровно один раз» для внешней почты недостижимо.

| Сбой | Что происходит | Тест |
|---|---|---|
| Повтор события `price.changed` | Новый минимум уже записан (`last_notified_price`) — второго уведомления нет | `BeaconCheckerIT` |
| Два события одного снижения одновременно | Строки маячков под `FOR UPDATE` — одно уведомление (без блокировки тест падает: 2) | `BeaconEmailDeliveryIT` |
| SMTP ошибка | `FAILED` + повтор RabbitMQ; успешная попытка → `SENT` | `BeaconEmailDeliveryIT` |
| Падение посреди отправки | Ключ Redis ещё не поставлен → повторная доставка отправит письмо | `ProcessedMessages` + unit-тесты |
| Брокер недоступен / не подтвердил | `published_at` пуст → через ≥ 1 мин relay публикует снова | `BeaconEmailDeliveryIT` |
| Первая публикация ещё идёт | Она ждёт не дольше 5 с, relay берёт записи старше 1 мин — не пересекаются | `BeaconEmailDeliveryIT` |
| Письмо в очереди или в DLQ | `published_at` есть → relay не трогает, повторы остаются за RabbitMQ | `BeaconEmailDeliveryIT` |
| Неадресуемое сообщение | Возврат по `mandatory` → «не опубликовано» | `BeaconEmailDeliveryIT` |
| Брокер принял, подтверждение потеряно | Relay опубликует копию; обработчик видит `SENT` и не отправляет второй раз | `BeaconEmailDeliveryIT` |
| Две копии одного письма обрабатываются **одновременно** | Строки уведомления блокируются (`FOR UPDATE`, по порядку id) от проверки до записи `SENT`: вторая копия ждёт и находит `SENT` — одно письмо (без блокировки тест падает: два) | `NotificationSendingIT` |
| Не подтверждено 24 ч | `FAILED` / `NOT_PUBLISHED` — **окончательная** причина. Если копия всё же дошла до брокера (подтверждение потеряно) и придёт позже, обработчик подтвердит её без отправки | `BeaconEmailDeliveryIT`, `NotificationSendingIT` |
| Копия после временной ошибки SMTP | `FAILED` с текстом ошибки — причина временная, копия отправляется | `NotificationSendingIT` |
| Сводка: пропущен запуск | Следующий запуск берёт все неопубликованные `DIGEST` | логика выборки |
| Сводка: сообщение уже в очереди / DLQ | Не собирается повторно (`published_at`) | `BeaconEmailDeliveryIT` |
| Несколько экземпляров | ShedLock на сводке и relay, `SKIP LOCKED` в relay | — |
| Зависший SMTP | Тайм-ауты 5 / 10 / 10 с → ошибка → повтор | конфигурация |

**Окончательные и временные отказы.** Окончательные причины (`EMAIL_NOT_VERIFIED`, `BEACON_INACTIVE`, `NOT_PUBLISHED`, `NotificationErrors.FINAL`) закрывают уведомление: любая копия письма подтверждается без отправки, и ошибка SMTP их не перезаписывает. Текст ошибки SMTP — причина временная: следующая попытка или копия отправит письмо.

**Почему `FOR UPDATE`, а не `SKIP LOCKED` в обработчике.** Relay держит строку заблокированной, пока публикует копию и записывает `published_at`. С `SKIP LOCKED` обработчик, получивший копию раньше коммита relay, подтвердил бы её без отправки — а relay эту строку больше не тронет: письмо пропало бы. Поэтому обработчик ждёт. Транзакция открыта на время SMTP (до ~25 с при наших тайм-аутах), потоков обработчика два — не больше двух соединений из пула.

**Остаточный риск (принят):** почтовый сервер принял письмо, а приложение упало до сохранения `SENT` (или тайм-аут во время передачи) → при повторной доставке письмо уйдёт ещё раз. Одновременная обработка двух копий дублей больше не даёт. Письма подтверждения email и сброса пароля в `notifications` не пишутся и relay не покрываются: если брокер недоступен, пользователь запрашивает ссылку снова.

## 4. Отписка
- В ссылке — 32 случайных байта, в БД только SHA-256; привязка к одному маячку (`email_tokens.beacon_id`), действие одно — пауза; 90 дней, многоразовая.
- Backend: только `POST` с токеном. **Требование к F5:** страница `/unsubscribe` не отправляет POST при загрузке, а показывает кнопку — иначе почтовые сканеры, исполняющие JavaScript, поставят маячок на паузу.
- Заголовок `List-Unsubscribe` есть; one-click по RFC 8058 (`List-Unsubscribe-Post`, DKIM) **не заявлен** — отложен до боевого почтового сервера (M21 или позже).

## 6. Ошибки, найденные по ходу
1. **M17: общий ключ идемпотентности.** `price.changed` уходит в две очереди, ключ `processed:v1:{messageId}` был один — один потребитель пропускал сообщение. Теперь `processed:v1:{consumer}:{messageId}`. Найдено интеграционным тестом.
2. **Ключ ставился до обработки** — падение посреди отправки теряло письмо. Теперь после.
3. **Письмо терялось, если брокер недоступен после коммита** — нет повторной публикации. Теперь `published_at` + relay.
4. **Сводка могла собрать книги повторно**, если её сообщение уже в очереди или в DLQ. Теперь выбирает только неопубликованные.
5. **Нет тайм-аутов SMTP** — зависший сервер навсегда занимал обработчик.

## 7. Ревью: что принято, что нет
| Замечание | Итог |
|---|---|
| Повторная доставка и дубли | Повтор события уже защищён БД; найден и закрыт обратный риск — потеря писем (п. 6.2–6.3) |
| Повтор «по возрасту QUEUED» создаёт дубли и обходит DLQ | **Принято** — моя ошибка в первом плане; введён `published_at` |
| Гонка первой публикации и relay | **Принято**; решено ограничением времени (5 с ≪ 1 мин), а не блокировкой на время сетевого вызова |
| Восстанавливать только допустимые | **Принято**; добавлен `delivery`, условия `QUEUED` + `INSTANT` + неопубликовано |
| Publisher confirms полностью | **Принято**: ack + не возвращено (`mandatory`); очереди устойчивые, сообщения постоянные |
| Статусы `PROCESSING`, `next_retry` | Не добавлены: повторы — у RabbitMQ, координация — `published_at` и блокировки |
| Ключ сводки «пользователь + дата» | Не нужен: ShedLock + выборка по статусу и `published_at` |
| Частично обновлённые статусы у сводки | Невозможны: `SENT`/`FAILED` — один UPDATE по всем уведомлениям письма |
| Старые ключи Redis у застрявших писем | Не относится: у каждой публикации новый `messageId`, M19 нигде не работала |
| Раунд 3: две копии одновременно (разные `messageId`, Redis не защищает) | **Принято**; блокировка строк уведомления до записи `SENT`. Отвергнуты: блокировка в Redis (второй источник истины), статус PROCESSING с арендой (истечение аренды). `SKIP LOCKED` отвергнут — терял бы письмо (см. п. 3) |
| Раунд 3: `NOT_PUBLISHED` при копии в очереди | **Принято**; окончательные причины отказа не дают отправки, временные (SMTP) — дают. Исправлена ошибочная фраза отчёта «копии нигде нет» |
| RFC 8058, DKIM | Отложено (п. 4) |
| Правило «рост → снова снижение» | Зафиксировано: только новый минимум (п. 2) |

## 8. Что проверено и что нет
- Unit-тесты: 165 из 165. Интеграционные — на локальных PostgreSQL 16, Redis, RabbitMQ вместо Testcontainers (нет Docker): 159 из 162; не запускаются три `MigrationIT`.
- Тесты гонок проверены «от обратного»: без блокировки маячков проверка цены даёт 2 уведомления, без блокировки уведомлений две копии дают 2 письма.
- Вживую (jar + Mailpit): письмо «Цена упала» с `List-Unsubscribe`, повтор той же цены — без письма, ниже — второе письмо, отписка без входа, сводка DAILY.
- **Не проверено:** `./mvnw verify` с Testcontainers (включая миграции V16–V18 на чистой базе) — нужен прогон с Docker; relay и сводка по реальному расписанию (логика покрыта тестами).

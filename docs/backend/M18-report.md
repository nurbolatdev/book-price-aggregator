# Отчёт M18 — изменения сверх плана и принятые решения

**Ветка:** `feature/m18-auth-v2` · **Дата:** 2026-10-23

Задание вехи — [M18-auth-v2.md](M18-auth-v2.md). Здесь собрано всё, что сделано **иначе, чем в задании, или сверх него**, и почему. Архитектурное решение о сессиях и очистке токенов — [ADR-004](../adr/ADR-004-refresh-token-sessions.md).

## 1. Сделано сверх плана (согласовано при приёмке)
| Что | Коммит | Суть |
|---|---|---|
| Семейства refresh-токенов | `feat: refresh token families and session limit` | Повтор отозванного токена завершает только его сессию, а не все сессии пользователя. Событие — в `system_events`. Миграция V14. |
| Лимит сессий | там же | Не больше 10 устройств (`JWT_MAX_SESSIONS`); сверх лимита завершается сессия, дольше всех не обновлявшаяся. |
| Очистка токенов | `feat: scheduled cleanup of expired auth tokens` | Ночью: refresh-токены через 30 дней после истечения, ссылки из писем через 7 дней; пакетами по 1000. Индексы V15. |
| Доработки по внешнему ревью | `fix: harden token families and session limit` | Старые токены пользователя → одно семейство; блокировка пользователя при входе (гонка двух входов); User-Agent в журнале обрезается; тест точной границы очистки. |
| Документация | `docs: describe token families and cleanup`, этот отчёт, ADR-004 | |

## 2. Отличия от задания и почему
| Задание | Сделано | Почему |
|---|---|---|
| Миграция `V11__auth_v2.sql` | `V13__auth_v2.sql` (+ V14, V15) | V11 и V12 заняты в M16–M17. Миграция уведомлений M19 станет **V16**. |
| Повтор отозванного refresh → отозвать **все** токены пользователя | Отзывается **семейство** (одна сессия) | Решение владельца: кража одной сессии не должна выбрасывать со всех устройств (ADR-004). |
| — | `users.created_at` → `TIMESTAMPTZ`, `notify_frequency` ограничен `INSTANT \| DAILY` | Соглашение проекта: время в `TIMESTAMPTZ`; защита от мусорных значений. |
| Регистрация (было: сразу выдавала токен) | `201 {userId, emailVerificationRequired: true}`, без токенов | По контракту `docs/03-api-contract.md`; вход — отдельным запросом. |
| Ответ входа (было: `{token, email, name}`) | `{accessToken, refreshToken, expiresIn, user}` | По контракту. **Старый React-фронтенд фазы 1 перестанет входить** — переделывается в F4. |
| — | Истёкший access-токен → 401 `TOKEN_EXPIRED` (не `UNAUTHORIZED`) | Фронт понимает, что надо обновить пару, а не выходить. |
| — | JWT-фильтр не обращается к БД, пользователь — из claims | Быстрее; access живёт 15 мин, этого достаточно. Токены старого формата (до M18) не принимаются. |
| Ошибки ссылок из писем не описаны | неизвестная/использованная/другого назначения → 400 `TOKEN_INVALID`, истёкшая → 401 `TOKEN_EXPIRED` | Единые коды из контракта. |
| — | Письмо уходит в очередь только после коммита транзакции | Откат регистрации не должен отправлять ссылку «в никуда». |
| Actuator по разделу 6 контракта | Публичный `/actuator/health` — только статус; `/actuator/info` и остальное — ADMIN | Раньше health показывал подробности всем. |
| `GET /me`: имя, email, emailVerified, notifyFrequency, weeklyDigest | плюс `id` и `role` | Фронту нужна роль, чтобы показать вход в админку. |
| Лимит search 60/мин | Только на `GET /api/v1/search`; подсказки — по общему 120/мин | Подсказки дёргаются на каждый ввод и быстро съели бы лимит поиска. |
| — | Без Redis лимиты отключаются на 30 с (WARN), API работает | Недоступный Redis не должен ронять вход и поиск. |
| — | nginx фронтенда передаёт `X-Forwarded-For`, в docker `server.forward-headers-strategy: native` | Иначе все пользователи за nginx — один IP, и лимиты регистрации срабатывали бы на всех сразу. |
| CORS: метод и заголовок `Authorization` | Ещё `Content-Type`, `X-Request-Id`; наружу отданы `Retry-After`, `X-Request-Id` | Фронт должен видеть `Retry-After` при 429. |
| — | `APP_CORS_ALLOWED_ORIGINS`, `RATE_LIMIT_ENABLED`, `MAIL_FROM`, `JWT_ACCESS_TTL`, `JWT_REFRESH_TTL` (вместо `JWT_EXPIRATION_MS`), `JWT_MAX_SESSIONS`, `APP_ADMIN_*` | Новые переменные — в `.env.example` и `docker-compose.yml` по правилам проекта. |

## 3. Исправления прошлых вех
- **`RabbitTopologyIT` (M17):** читал очередь сразу после отправки — гонка с асинхронной публикацией. Теперь ждёт сообщение до 5 с.
- **`AbstractListenerIT` (M17):** с появлением обработчика писем старые письма из очереди падали в DLQ, которую читают эти тесты. Отправка писем там подменена.

## 4. Решения, принятые при обсуждении
| Вопрос | Решение |
|---|---|
| Как чистить токены | Плановая задача в приложении, удаление по сроку после `expires_at`, пакетами (варианты — в ADR-004) |
| Можно ли удалять отозванные токены сразу | Нет: без них не обнаружить повтор украденного токена |
| Где хранить аудит | В `system_events`, не в таблицах токенов |
| Писать ли IP в журнал | **Нет** — конфиденциальные персональные данные |
| Семейства и лимит сессий | Делать в M18 |
| Старые токены без цепочек | Одно семейство на пользователя (осторожный вариант) |
| Гонка одновременных входов | Блокировка строки пользователя при входе |
| Миграцию V14 исправить в файле или новой миграцией | В файле: ветка ещё не влита, на проде V13–V15 применятся вместе |

## 5. Внешнее ревью: что принято, что нет
| Замечание | Итог |
|---|---|
| V14 могла разнести токены одной цепочки по разным сессиям | **Принято**, исправлено (одно семейство на пользователя) |
| Повтор A после A→B: завершить сессию, записать событие, не выдать пару, не тронуть другое устройство | Уже было и покрыто тестом |
| Лимит должен завершать самую давнюю **по обновлению** | Уже было (LRU) и покрыто тестом |
| Гонка двух одновременных входов | **Принято**, исправлено; тест без блокировки падает с 11 сессиями |
| Граница сроков, UTC, NULL, отдельные транзакции, индексы | UTC, транзакции и индексы уже были; `NULL` невозможен (`NOT NULL`); **добавлен** тест точной границы |
| В журнале — без токенов и секретов; сброс пароля завершает все сессии | Уже было; **добавлены** обрезка User-Agent и проверка, что токена нет в журнале |

## 6. Что проверено и что нет
- Unit-тесты: 154 из 154.
- Интеграционные — на локальных PostgreSQL 16, Redis, RabbitMQ 3.12 вместо Testcontainers (в среде нет Docker): 131 из 134. Не запускаются три теста `MigrationIT` — им нужен контейнер; новый тест V14 проверен вручную на локальной базе.
- Вживую (jar + Mailpit 1.21): письма подтверждения и сброса, одноразовые ссылки, ротация и выход, первый админ из переменных окружения, 403 для USER на `/admin`, 429 с `Retry-After: 60`, работа API без Redis, обновление базы с токенами до V14.
- **Не проверено:** `./mvnw verify` с Testcontainers и ночная очистка по расписанию в 03:30 (логика очистки покрыта тестами). Нужен прогон в CI или локально с Docker.
